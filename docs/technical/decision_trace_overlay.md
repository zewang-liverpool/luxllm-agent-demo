\# LLM Decision Trace Overlay



\## 1. Overview



The LLM Decision Trace Overlay is an extension of the LuxLLM-Agent Season 3 isometric replay viewer.



Its purpose is to connect visual replay frames with structured decision-trace information, so that the user can inspect not only what happened in the game, but also how the agent's decision was produced.



The overlay supports the main research question:



> How can structured decision tracing and rule-based action verification support the inspection and evaluation of LLM-based agents in Lux AI Season 3?



The overlay also directly supports the third sub-research question:



> How can replay-grounded decision traces help analyse the relationship between LLM strategy, decision source, action execution, and game outcome?



In the current implementation, the overlay displays step-aligned decision information next to the replay map. This makes the viewer a replay-grounded decision inspection interface rather than only a visual replay tool.



\---



\## 2. Motivation



A standard replay viewer can show unit movement, map state, and score progression. However, it does not explain why an agent made a particular decision.



For LLM-based agents, this is especially important because:



\* LLM decisions may be difficult to interpret from actions alone;

\* a visible action may come from a fresh LLM decision, cached LLM plan, fallback logic, or rule-based logic;

\* final win/loss results do not explain decision quality;

\* fallback and rule verification may change the final executed action;

\* cached plans may continue to influence later frames.



The LLM Decision Trace Overlay addresses this problem by displaying decision provenance, LLM strategy, fallback status, risk filter information, and score context during replay playback.

\## 4. Overlay Data Generation



The overlay data is generated by:



```text

tools/build\_run008\_decision\_trace\_overlay.py

```



This script reads:



```text

data/isometric\_replay\_frames\_run008.json

logs/decision\_trace.jsonl

logs/decision\_log.jsonl

```



and writes:



```text

data/run008\_decision\_trace\_overlay.json

```



The replay frame file contains the visual frame sequence for Run008. The decision trace logs contain step-level information about the agent's decision source, fallback status, LLM mode, cache usage, risk filter status, and score context. The LLM decision log contains fresh LLM plan information, including global objectives and unit intents.



The script aligns these sources by step number.



\---



\## 5. Step Alignment



The overlay generation script aligns replay frames with trace rows.



The current generated result is:



```text

frames: 506

trace rows: 1009

llm decision rows: 23

matched step trace frames: 505

matched exact LLM frames: 23

matched recent LLM frames: 506

```



This means that nearly all replay frames have a matched step trace. Only 23 frames correspond to exact fresh LLM decision steps, but every frame can still be associated with the most recent LLM plan.



This is important because the LLM is not called at every frame. The agent may act under a cached or recent LLM plan across multiple game steps.



The overlay therefore distinguishes between:



\* exact fresh LLM decision frames;

\* frames using a recent LLM plan;

\* frames with step trace but no fresh LLM call;

\* frames with fallback or rule-only decision sources.

\## 7. Viewer Integration



The new viewer file is generated from the previous isometric viewer:



```text

docs/viewers/s3\_isometric\_battle\_viewer\_v09n12c3.html

```



The generated overlay version is:



```text

docs/viewers/s3\_isometric\_battle\_viewer\_v09n12d\_trace\_overlay.html

```



The viewer loads overlay data from:



```text

../../data/run008\_decision\_trace\_overlay.json

```



The overlay is implemented as a fixed-position panel in the browser. It updates continuously during playback by reading the current frame index and displaying the corresponding item from the overlay JSON.



The panel supports keyboard toggling:



```text

H: hide/show decision trace overlay

```



This makes the overlay useful both for live demonstration and for clean screenshot capture.

\## 8. Displayed Information



The overlay displays the following information.



\### 8.1 Frame and step



Shows the current replay frame and game step.



Example:



```text

Frame / Step: 77 / 77

```



This links the visual replay state to the corresponding trace record.



\### 8.2 Phase



Shows the current game phase, such as:



```text

early\_exploration

```



This helps explain whether the agent is exploring, securing candidates, or performing another strategic behaviour.



\### 8.3 Decision source



Shows where the decision came from.



Possible values include:



```text

llm\_fresh

cached\_llm

fallback

rule\_fallback

rule\_player

rule\_only

```



This is central to the project's decision-trace contribution.



\### 8.4 LLM model



Shows the LLM backend associated with the trace.



Examples:



```text

qwen3:32b

deepseek-r1:32b

```



\### 8.5 Objective and risk posture



The overlay shows the current LLM global plan, including:



```text

main\_objective

risk\_posture

reason

```



This helps connect LLM planning to visible game behaviour.



\### 8.6 Fallback status



The overlay shows whether fallback was used and, when available, why it was used.



Example:



```text

Fallback: Yes: force\_rule\_only

```



This helps inspect when rule-based behaviour replaces or supports LLM behaviour.



\### 8.7 Risk filter status



The overlay shows whether the risk-aware filter was enabled and whether it changed targets or actions.



This helps inspect how rule-based safety mechanisms affect execution.



\### 8.8 Score context



The overlay displays the current score context:



```text

P0 43 : P1 0

```



This links decisions to game outcome progression.



\### 8.9 Unit intents



The overlay displays selected unit-level intents, such as:



```text

Unit 0: MOVE\_TO\_RELIC\_CANDIDATE

priority=0.85

risk=low

target=\[5, 10]

reason=unit is close to a relic candidate tile

```



This makes the LLM plan more concrete and interpretable.

\## 9. Example Interpretation



A replay frame may show the following overlay information:



```text

Frame / Step: 77 / 77

Phase: early\_exploration

Source: rule\_only

LLM Model: qwen3:32b

Objective: explore\_and\_secure\_candidate

Risk Posture: balanced

Fallback: Yes: force\_rule\_only

Risk Filter: disabled

Summary: Using most recent LLM plan from step 60: explore\_and\_secure\_candidate.

```



This can be interpreted as follows:



\* the replay is currently showing step 77;

\* no fresh LLM call happened exactly at this frame;

\* the viewer is using the most recent LLM plan from step 60;

\* fallback or rule-only behaviour is active;

\* the visible actions should therefore be interpreted as rule-supported execution under a recent strategic plan.



This is more informative than a standard replay because it explains the provenance of the behaviour.

The LLM Decision Trace Overlay contributes to the dissertation in several ways.



\### 10.1 It supports replay-grounded inspection



The overlay links replay frames to decision trace records. This supports qualitative analysis of agent behaviour.



\### 10.2 It demonstrates decision provenance



The viewer shows whether behaviour comes from LLM decisions, cached plans, fallback logic, or rule-based policies.



\### 10.3 It supports action-verification analysis



Fallback and risk filter information make it easier to inspect when the system intervenes between LLM strategy and executable action.



\### 10.4 It provides strong visual evidence

\### 10.5 It connects implementation and evaluation



The overlay connects logs, metrics, replay frames, and visual inspection into one interface.

\## 11. Evaluation Value



The overlay is useful for both qualitative and quantitative evaluation.



\### 11.1 Qualitative evaluation



The overlay can be used to inspect representative examples:



\* a fresh LLM decision frame;

\* a cached LLM plan frame;

\* a fallback frame;

\* a risk-filtered frame;

\* a failure case where the strategy did not lead to a good outcome.



\### 11.2 Quantitative evaluation



The overlay data comes from structured logs that can also be aggregated into metrics:



\* number of matched trace frames;

\* number of exact LLM decision frames;

\* number of recent LLM plan frames;

\* decision-source distribution;

\* fallback frequency;

\* risk filter change frequency;

\* score progression.



This supports the argument that LuxLLM-Agent provides an evaluation framework rather than only a replay visualiser.

\## 12. Limitations



The current overlay has several limitations.



First, the overlay depends on available trace logs. If the replay frames and decision logs come from different runs, the overlay must be clearly labelled as a prototype or aligned inspection view.



Second, not every frame corresponds to a fresh LLM decision. This is expected because the system uses strategy caching, but it means the viewer must distinguish exact LLM decision frames from recent-plan frames.



Third, the overlay does not prove that a strategy is optimal. It shows what the system believed or selected, but further analysis is needed to evaluate whether the decision was strategically good.



Fourth, the overlay currently focuses on selected trace fields. More detailed future versions could show verifier decisions, rejected plans, alternative candidate actions, or before/after risk-filter changes.



These limitations should be discussed in the dissertation as part of the critical reflection.



\---



\## 13. Future Improvements



Possible future improvements include:



\* adding a timeline marker for fresh LLM decision steps;

\* highlighting fallback frames on the replay timeline;

\* showing rejected actions and verifier reasons;

\* showing before/after actions when the risk filter changes a plan;

\* linking overlay rows to raw JSON trace records;

\* adding filters for decision source types;

\* supporting multiple match replays instead of only Run008;

\* allowing comparison between qwen3:32b and deepseek-r1:32b traces in the viewer.



These improvements would make the viewer more useful as a general LLM-agent inspection tool.



\---



\## 14. Summary



The LLM Decision Trace Overlay turns the Season 3 replay viewer into a replay-grounded decision inspection interface.



It connects visual game state, LLM planning, decision source, fallback behaviour, risk filtering, score context, and unit-level intent. This directly supports the project's research focus on structured decision tracing and rule-based action verification.



For the COMP702 dissertation, the overlay is strong evidence that the project goes beyond building an LLM game agent. It provides a tool for inspecting and evaluating how LLM-based agents make and execute decisions in a complex multi-agent environment.
